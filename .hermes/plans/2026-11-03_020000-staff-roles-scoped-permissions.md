# خطة: أدوار الطاقم والصلاحيات المحدودة بنطاق (مدير منصة · مشرف مرحلة · محرر صلاحيات)

> الحالة: **proposed** — خطة فقط. لا تنفيذ ولا migration ولا نشر قبل موافقة يوسف على القرارات (D1–D5) ثم «ابدا».
> المالك: يوسف (القرارات) · المنفّذ: Hermes · التاريخ: 2026-11-03

## 1. الهدف
1. إضافة **مدير منصة** يشغّل المنصة يومياً بدون صلاحيات النظام الحساسة.
2. إضافة **مشرف تعليمي** محصور في مرحلة/صف/مادة محددة (مثلاً: الابتدائي فقط، أو الصف الرابع فقط).
3. **محرر صلاحيات موسّع**: شاشة يحدد فيها المشرف العام لكل عضو طاقم صلاحيات دقيقة + نطاقها، بدل الاعتماد على الدور وحده.

## 3. التصميم المقترح: دور كقالب + صلاحيات + نطاق
**المبدأ:** الدور يحدد *السقف* والقالب الافتراضي؛ الصلاحيات الفعلية صفوف في جدول، كل صف = (صلاحية × نطاق). الخادم (RLS/RPC) هو المرجع؛ الواجهة تخفي فقط.

### 3.1 الأدوار
| الدور (قيمة DB مقترحة) | التسمية | السقف |
|---|---|---|
| `admin` (موجود) | مدير النظام / المالك | كل شيء + إدارة المستخدمين والصلاحيات. لا يُمنح إلا من admin |
| `platform_manager` (جديد) | مدير المنصة | كل التشغيل؛ **بدون** إدارة الأدوار/الصلاحيات، حذف الحسابات، إعدادات المساعد الذكي (حسب D1) |
| `supervisor` (جديد) | مشرف تعليمي | صلاحيات تعليمية فقط وداخل نطاق مرحلة/صف/مادة إلزامي |
| `content_editor` (موجود) | محرر محتوى | المناهج والدروس (يمكن تقييده بنطاق لاحقاً) |
| `teacher`, `parent` | كما هي | لا تغيير |

### 3.2 كتالوج الصلاحيات (مسودة — D2)
`content.edit` · `content.publish` · `lessons.review` · `recordings.review` · `teachers.assign` · `schedule.manage` · `families.view` · `families.manage` · `bookings.manage` · `subscriptions.view` · `subscriptions.manage` · `analytics.view` · `settings.edit` · `ai_tutor.manage`
- `users.manage` (الأدوار/الصلاحيات/حذف الحسابات) **غير قابلة للمنح** — admin فقط.

### 3.3 النطاق
`scope_kind ∈ {all, stage, grade, subject}` + `scope_value` (مثل `primary` أو `g4` أو مفتاح مادة). صلاحيات غير تعليمية (subscriptions/settings/analytics) نطاقها `all` فقط.

### 3.4 قاعدة البيانات (ملفات جديدة فقط)
- جدول `staff_permissions(user_id, capability, scope_kind, scope_value, granted_by, granted_at)` + unique + RLS: القراءة للشخص نفسه وadmin؛ لا كتابة مباشرة.
- جدول `staff_permission_audit` (insert-only) لكل منح/سحب.
- دالة `has_capability(p_cap text, p_grade_id text default null, p_subject_key text default null)` security definer stable: admin → true؛ وإلا يطابق النطاق (stage عبر `grades.stage`، subject عبر `curriculum_subjects.grade_id`).
- RPCs: `admin_grant_capability`, `admin_revoke_capability`, `admin_apply_role_preset`, `my_capabilities()`.
  - منع: منح نفسك، منح `users.manage`، منح صلاحية خارج سقف الدور، supervisor بلا نطاق.
- توسيع `admin_set_user_role` + قيد `profiles_role_check` بالدورين الجديدين (migration جديدة)، ويطبّق القالب الافتراضي في نفس المعاملة.
- **لا نغيّر معنى `is_admin()`**. نضيف سياسات RLS بشكل *إضافي* لكل وحدة: `is_admin() or has_capability(...)`.

### 3.5 الواجهة
- `my_capabilities()` تُحمّل مع الجلسة؛ `navConfig.js` يقبل `capability` بجانب `roles` (توافق خلفي).
- تبويب «المستخدمون والصلاحيات»: **محرر صلاحيات** = مصفوفة (صلاحية × نطاق) لكل عضو طاقم، مع اختيار المرحلة/الصف/المادة، ومعاينة «ماذا سيرى».
- قوائم المناهج/المراجعة تُفلتر حسب النطاق (UX فقط؛ RLS هو الحارس).
- التسميات الجديدة في `adminUsers.js` و`AuthGate.jsx` و`navConfig.js`.

## 7. ✅ قرارات يوسف 2026-11-03
- **D2 = (أ):** «محرر الصلاحيات الموسّع» = شاشة تحرير صلاحيات كل موظف ونطاقها بالتفصيل. لا دور جديد للمحتوى.
- **D1:** مدير المنصة **لا** يعدّل كتالوج الاشتراكات (عرض فقط)، **لا** إعدادات المساعد الذكي، **لا** حذف حسابات ولا تغيير أدوار.
- **D5:** مدير المنصة **يمنح الموظفين صلاحيات أقل من صلاحياته**. قيود إلزامية على الخادم:
  - يمنح فقط صلاحية يملكها هو، وبنطاق ضمن نطاقه أو أضيق.
  - لا يمنح نفسه، ولا يمنح/يسحب من `admin` أو `platform_manager` آخر.
  - لا يمنح `users.manage` ولا `subscriptions.manage` ولا `ai_tutor.manage`.
  - كل منح/سحب في `staff_permission_audit`؛ admin يرى السجل ويلغي أي منح.
- **D4:** النطاق = مرحلة أو صف أو مادة حسب الاختيار.
- **D3 = يرى ويعدّل:** المشرف يرى أطفال نطاقه وتقدّمهم ويعدّل. ⚠️ مخاطرة عالية (قاصرون) — ضوابط مقترحة للمرحلة 5:
  - «النطاق» للطفل = صف الطفل (`grade`) أو مادة مشترك فيها؛ يُحسم الربط الفعلي بفحص الإنتاج (المرحلة 1): لم يُتحقق بعد من عمود صف الطفل في جدول الأطفال (المتحقق فقط: `curriculum_subjects.grade` نص حر في `20261024120000_phase3_real_data.sql:12` و`curriculum_subjects.grade_id` مرتبط بـ `grades`).
  - التعديل عبر RPC بحقول مسموحة فقط (مثل: الصف، الجدول، المعلم المسند، ملاحظات تعليمية)، **بلا** حذف طفل، **بلا** تعديل بيانات ولي الأمر/الاشتراك/الدفع، **بلا** نقل طفل خارج نطاق المشرف.
  - سجل تدقيق لكل تعديل على بيانات طفل.
  - صلاحيتان منفصلتان: `children.view` و`children.edit` حتى يقدر admin يعطي العرض بدون التعديل.
  - قائمة الحقول المسموحة تُعرض على يوسف قبل كتابة الـ RPC.

## 7-ب. القرارات المفتوحة الأصلية (للأرشيف)
- **D1 — حدود مدير المنصة:** هل يُستثنى من: إدارة الأدوار ✔ (مقترح)، حذف الحسابات ✔، إعدادات المساعد الذكي؟، كتالوج الاشتراكات (عرض فقط أم تعديل)؟
- **D2 — «محرر صلاحيات موسع»:** المقصود (أ) شاشة تحرير صلاحيات دقيقة لكل عضو (المقترح) أم (ب) دور جديد = محرر محتوى بصلاحيات أوسع؟
- **D3 — المشرف وبيانات الأطفال:** هل يرى أطفال صفوف نطاقه وتقدّمهم؟ (مقترح: لا في المرحلة الأولى؛ فقط الدروس والمعلمين).
- **D4 — مستوى النطاق:** المرحلة فقط، أم المرحلة + الصف + المادة؟ (مقترح: الثلاثة، لأن الجدول يدعمها).
- **D5 — من يمنح الصلاحيات:** admin فقط (مقترح)، أم يُسمح لمدير المنصة بمنح صلاحيات أدنى منه؟
