# خطة تطوير وتنظيم إدارة الأدوار والتشغيل — فاهم

> **For Hermes:** يوسف فوّض البدء بالتنفيذ المحلي والتوثيق في 2026-10-27. لا يشمل ذلك تغيير قاعدة البيانات الحية أو بياناتها أو RLS، ولا commit/push أو نشر أو اختبار كتابة في الإنتاج؛ لكل منها تفويض مستقل.

**الهدف:** تأهيل المنصة المنشورة حالياً على المستودع والخادم والمتصلة بقاعدة بيانات حية — حسب إفادة يوسف في 2026-10-27 — قبل نقلها إلى خادم خاص. نثبت كل ادعاء بالأدلة المتاحة، وننظم إدارة الطلاب والمعلمين والجدول والمناهج والتكليفات وصلاحيات الأدوار دون اختبار كتابة أو تغيير عشوائي في الإنتاج.

**البنية:** مراجعة حقيقة التشغيل والتوثيق أولاً، ثم إصلاحات واجهة قليلة المخاطر، وبعدها اختبار صلاحيات وتدفقات العمل على بيئة اختبار وحسابات أدوار. أي تعديل قاعدة بيانات/سياسات يكون فقط عند إثبات فجوة، عبر migration جديدة واختبارات رفض وسماح.

**التقنيات التي تثبتها الشيفرة:** React 19، Vite 6، React Router 7، عميل Supabase للمصادقة والبيانات، وNode API/SQLite محلي مستقل للتطوير. وصف README السابق بأن المستودع نموذج محلي بلا قاعدة مشتركة كان قديماً ومتناقضاً مع الشيفرة والإفادة الأحدث؛ عُدّل README لتوضيح أن API/SQLite المحلي أداة منفصلة لا تمثل قاعدة المنصة المنشورة.

## ترتيب الأولويات

### P0 — تثبيت حقيقة المنصة وحدود الإطلاق

**المالك:** يوسف لتأكيد واقع التشغيل (أفاد به بالفعل)؛ المنفذ يجمع أدلة قراءة فقط ولا يلمس أسرار الاتصال.

1. تثبيت أن المستودع يحمل تطبيقاً متصلاً بـSupabase: تحققنا من عميل Supabase في `src/lib/supabase.js` ومن استخدامه في `AuthContext.jsx` والواجهات الإدارية. إفادة يوسف تؤكد أن نسخة التشغيل متصلة بقاعدة حية؛ لا نستخرج أو نعرض مفاتيح البيئة لإثبات ذلك.
2. إعداد جدول حقيقة لكل ميزة: ملف الواجهة، مصدر البيانات، هل الحفظ محلي أم API/Supabase، هل السياسة موجودة، وهل ثبت تطبيقها خارجياً. وجود migration في المستودع لا يثبت وحده تطبيقها على قاعدة الإنتاج.
3. تحديث README لإزالة وصف «نموذج محلي بلا قاعدة مشتركة»؛ وشرح أن `server/server.js` وSQLite المحلية أداة منفصلة لا تمثل خلفية المنصة المنشورة. يسجل الفرق بين ما أكده المالك وما اختُبر مباشرة.

**معيار القبول:** وثائق لا تتعارض مع حقيقة التشغيل التي أكدها يوسف، وسجل يفصل بين (موجود في الكود / متصل حسب المصدر أو إفادة المالك / مطبق خارجياً / اختبر فعلياً).

### P1 — إغلاق الفجوات الواضحة في تجربة الإدارة

**المالك:** مطور الواجهة؛ لا تغيير صلاحيات قاعدة البيانات تلقائياً.

1. **منجز جزئياً في 2026-10-27:** في `src/components/admin/LessonReview.jsx` أصبحت أخطاء Supabase حالة خطأ مستقلة عن الفراغ مع زر إعادة محاولة؛ أضيف اختبار وحدات يغطي النجاح والفراغ والفشل وغياب الخدمة. لا يدعي هذا اكتمال المراجعة أو اختبارها بحساب admin على الإنتاج.
2. **منجز جزئياً في 2026-10-27:** في `src/components/myspace/AssignStudents.jsx` أضيفت حالة تحميل/خطأ/إعادة محاولة ورسالة عامة عند فشل الاستعلام؛ أضيفت اختبارات نقية لمحول نتائج الاستعلام. لم تُختبر الواجهة داخل جلسة إدارية، ولم تتغير صلاحيات الخلفية أو عمليات الإسناد.
3. **في `src/components/myspace/TeacherRoster.jsx` — إصلاح محلي أولي:** حالة خطأ عامة وإعادة محاولة للطلاب والجدول، منع بقاء التحميل عند غياب الخدمة/المستخدم، منع تسريب أخطاء الاستعلام، وتعطيل زر RPC أثناء الطلب؛ اختبارات وحدة 15/15 والبناء ناجحان في الجولة. ما زال الاختبار المرئي والمأذون غير منفذ، كما لم تُختبر صلاحية الخلفية على بيئة اختبار.
4. في أقسام الإدارة والتنقل: توحيد أسماء ومداخل إدارة المستخدمين، الطلاب والإسناد، الجدول، المواد، ومراجعة الدروس؛ وضع كل عملية في القسم الإداري المناسب دون تكرار لوحات متنافسة.

**اختبارات:** اختبارات وحدات لحالات الخطأ/الفراغ والقرارات المستخرجة، ثم build. اختبار متصفح مرئي للصفحات والتفاعلات الممكنة دون تسجيل دخول غير مصرح به.

**معيار القبول:** لا يمكن الخلط بين خطأ التحميل والبيانات الفارغة؛ الأدوات الإدارية لا تظهر في مساحة المعلم/الأسرة؛ العمليات الحساسة لا تعرض نجاحاً كاذباً.

### P1 — إثبات الصلاحيات لكل دور

**المالك:** مطور الواجهة وقاعدة البيانات؛ يتطلب بيئة اختبار وحسابات اختبار مأذوناً بها.

1. تتبع الحماية من `src/routes.js` و`AuthGate` و`src/navigation/navConfig.js` حتى كل لوحة/مكوّن. اختبر العرض والصلاحية الخلفية منفصلين: إخفاء الرابط وحده ليس حماية.
2. جهز مصفوفة سماح/رفض لحسابات admin وteacher وcontent_editor وparent، وأضف child/guest فقط حيث المسار مقصود أن يكون متاحاً.
3. اختبر أمثلة أساسية: المعلم يقرأ طلابه المسندين ولا يقرأ غيرهم؛ لا يستطيع الإسناد أو تعديل الجدول؛ يستطيع رفع مسودة ضمن مادته فقط؛ لا يستطيع اعتماد أو نشر؛ ولي الأمر لا يرى بيانات أسر أخرى؛ المحرر يراجع المحتوى دون صلاحيات إدارة المستخدمين أو بيانات الأطفال إلا ما تسمح به سياسة محددة.
4. لا تستخدم حساب ولي أمر إنتاجي ولا تُجرِ اختبارات كتابة على الإنتاج. إذا تعذر توفير حساب اختبار/بيئة آمنة، سجّل التحقق كـ«غير منفذ» ولا تستنتج النجاح.
5. راجع سياسات RLS والمنح والدوال المساعدة فقط بعد تحديد اختبار فاشل يثبت ثغرة. أي إصلاح DB في migration جديدة، واختبار سماح ورفض قبل التطبيق وبعده، دون تعديل migrations قديمة أو `schema.sql`.

**معيار القبول:** مصفوفة اختبار لكل دور، تشمل طلبات مباشرة وعمليات API/RLS وليس عناصر الواجهة فقط؛ كل سماح ورفض متوقع مثبت بنتيجة اختبار قابلة لإعادة التنفيذ.

### P2 — تحديد نظام التكليفات قبل بنائه

**المالك:** يوسف يحدد السياسة الأكاديمية؛ المنفذ يجري جرداً للموجود ثم يقدّم قراراً مقترحاً.

1. تتبع جميع نتائج بحث التكليفات من JSX وAPI والجداول والسياسات؛ لا تعتمد على عدد نتائج بحث واحد لإثبات الغياب.
2. إن لم يوجد تدفق عامل، وثّق قراراً قصيراً يحدد: من ينشئ التكليف، لمن يعيّنه، موعد التسليم، المرفقات المسموحة، كيف يسلّم الطالب، من يصحح/يراجع، حالات التكليف، الإشعارات المطلوبة، والاحتفاظ بالبيانات.
3. بعد اعتماد النموذج فقط: صمم أصغر تدفق قابل للاختبار. المسودة: المعلم ينشئ تكليفاً لطلابه المسندين/مادته؛ الطالب أو ولي الأمر يرى المطلوب ويسلّم؛ المعلم يراجع؛ الإدارة تراقب الإعدادات والتقارير. حدّد تفويض ولي الأمر بالنسبة لسن الطفل قبل اعتماد تدفق التسليم.
4. ابدأ باختبارات سلوك وصلاحيات، ثم قاعدة البيانات والتخزين بحد أدنى من البيانات. لا تنشئ صفحة أو تبويباً وهمياً قبل اتصال العملية الفعلية.

**معيار القبول:** نموذج حالات معتمد، ومخطط أدوار وبيانات، واختبارات تثبت منع التسليم/القراءة بين الطلاب والأسر غير المرتبطة؛ لا بيانات أطفال حقيقية في بيئة التطوير.

### P2 — اختبار قبول من البداية إلى النهاية

**المالك:** QA/يوسف للموافقة على حسابات الاختبار.

1. سيناريو الإدارة: تفعيل/دعوة معلم، إسناد مادة وطالب، إنشاء جدول، متابعة درس مرسل ومراجع.
2. سيناريو المعلم: يرى إسناداته فقط، يضيف رابط الحصة ضمن صلاحياته، ينشئ مسودة ويرسلها، ولا يستطيع نشرها أو تعديل جدول الإدارة.
3. سيناريو الأسرة/الطالب: يرى بياناته وحصصه ومحتواه المنشور فقط، ولا يصل إلى أدوات الإدارة أو بيانات الآخرين.
4. سيناريو الاستثناء: انقطاع/رفض الاستعلام، قائمة فارغة حقيقية، مستخدم بلا إسناد، وحساب بدور غير مخول.
5. احذف بيانات الاختبار والملفات بعد الاختبار وفق إجراء آمن وموافق عليه؛ لا تحذف سجلات الإنتاج أو عينات غير مفهومة.

**معيار القبول:** تقرير يبين المسار الذي اختبر، الحساب/البيئة بصيغة غير حساسة، نتيجة كل خطوة، وأي نقطة لم تختبر. لا يساوي نجاح البناء أو فتح الصفحة نجاح تدفق الاستخدام.
